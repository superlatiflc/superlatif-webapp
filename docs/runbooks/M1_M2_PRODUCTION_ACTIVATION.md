# Runbook — M1 + M2 Production Activation (pilot)

**Scope:** turn on student sign-in (M1, ADR-072/073) and Sejoli purchase → access (M2, ADR-074) on Production for one pilot product.
**Status:** DRAFT for founder review. Nothing in this document has been executed.
**Evidence it builds on:** `docs/audit/OD02_M1_STAGING_ACCEPTANCE.md`, `docs/audit/OD01_M2_STAGING_ACCEPTANCE.md`.

Every step below needs the founder's explicit go before it starts. Each step lists who acts, the action, the checkpoint that must pass before the next step, and its rollback. **If a checkpoint fails, stop, roll back that step only, and report.** Purchase, grant, attempt, and audit rows are evidence and are never deleted as a rollback (CLAUDE.md).

Roles:
- **Founder** — approves each step and acts in dashboards (Vercel, DNS, Supabase, WordPress admin).
- **Operator** — runs commands on the WordPress host (`wp-cli`) and the database scripts.
- **Engineer** — read-only verification after each step.

Secrets are generated by the founder or operator, entered directly into the target system, and never pasted into chat or tickets.

## 2. Activation steps

### S1 — Domain `app.superlatif.id`
- **Founder:** add the domain to the Vercel project (Production), then create the DNS record the Vercel dashboard shows at the DNS host. Do not touch `akademi.superlatif.id`.
- **Checkpoint:** `https://app.superlatif.id` serves the same `dpl_…` as the `vercel.app` alias, TLS valid, `/auth/bridge/start` still 404.
- **Rollback:** remove the domain from Vercel and the DNS record.

### S2 — Plugin 1.2.1 on live WordPress, inert
- **Operator:** upload ZIP 1.2.1 (Plugins → Add New → Upload) and activate. Do **not** add any client yet.
- **Checkpoint:** version 1.2.1 active, tables `…_superlatif_bridge_codes` and `…_superlatif_bridge_events` exist and are empty, an ordinary Sejoli login still lands on the member area, no checkout regression.
- **Rollback:** deactivate, then delete (uninstall drops only its own tables).

### S3 — Sign-in client (M1), no webhook yet
- **Operator:** in live `wp-config.php`, add client `superlatif-web-production` with a **new** `secret` (≥ 32 chars), `redirect_uri` `https://app.superlatif.id/auth/bridge/callback`, `environment` `production`. **No `webhook_secret` yet. Never `vercel_protection_bypass`.**
- **Founder (Vercel Production env):**
  - `WP_BRIDGE_BASE_URL=https://superlatif.id`;
  - `WP_BRIDGE_CLIENT_ID=superlatif-web-production`;
  - `WP_BRIDGE_CLIENT_SECRET=<same new secret>`;
  - `APP_BASE_URL=https://app.superlatif.id`;
  - `FEATURE_STUDENT_LOGIN=true`.

  Then redeploy. The build gate refuses an incomplete bridge configuration.
- **Checkpoint:**
  - the build passes;
  - the WordPress error log has no `ignoring client`;
  - on `https://app.superlatif.id/signin` the founder signs in once with a real account (T1);
  - exactly one identity and one session are created in Production;
  - exam actions still answer `writes_disabled`.
- **Rollback:** `FEATURE_STUDENT_LOGIN=false` and redeploy (routes return 404). Remove the client from `wp-config.php`.

### S4 — Pilot catalogue
- **Operator:** dry run first:
  ```bash
  DATABASE_URL=<prod> node --experimental-transform-types packages/db/scripts/load-production-catalogue.ts --file=<approved catalogue.json> --expect-ref=mfqfkxtrckacrwxltmxg
  ```
  The founder reviews the plan. Every product must show `create`.
- **Then apply:**
  ```bash
  ... --apply --confirm=APPLY-mfqfkxtrckacrwxltmxg
  ```
- **Checkpoint:** a re-run of the dry run shows `exists` for every product; the reconciliation report (§4) shows `OK`.
- **Rollback:** none needed while nothing is sold. To stop a product from granting access, retire its SKU mapping through a versioned change (a new mapping row), not a delete.

### S5 — Commerce on, writes still frozen
- **Founder (Vercel Production env):** set `SEJOLI_WEBHOOK_SIGNING_SECRET` to a **new** value (≥ 32 chars, not the sign-in secret) and `FEATURE_COMMERCE_SYNC=true`, then redeploy.
- **Checkpoint:** the build passes, and an unsigned `POST` probe to the webhook answers **503 `WRITES_DISABLED`**. That proves the route is configured and still frozen.
- **Rollback:** `FEATURE_COMMERCE_SYNC=false` and redeploy (404).

### S6 — Webhook secret on live WordPress
- **Operator:** add `webhook_secret` (same value as S5) to `superlatif-web-production`.
- **Checkpoint:** the next status change of any order creates an outbox row that is retried with `last_error = http_503:WRITES_DISABLED`. The plugin keeps it pending and nothing is lost.
- **Rollback:** remove `webhook_secret`. Delivery stops; already-queued rows keep retrying until they give up (about 22 h) and stay in the table.

### S7 — Open writes (launch decision G9)
- **Founder:** `PRODUCTION_WRITES_ENABLED=true`, then redeploy.
- **Checkpoint:**
  - queued events deliver with `202` (`last_error` cleared);
  - the reconciliation report shows the expected purchases;
  - Vercel logs show `commerce_webhook.accepted` and no `commerce_webhook.rejected`.
- **Rollback:** `PRODUCTION_WRITES_ENABLED=false` and redeploy. Events queue again (503) and nothing is lost. Exam writes freeze too.

### S8 — Founder test purchase
- **Founder:** buy the pilot product with a real account. Use admin "completed" if the payment cannot be made.
- **Checkpoint:** within seconds, purchase `paid` with one grant and access `true` (read-only check). The account can start the pilot content. Then cancel or refund that order, and confirm only that grant is revoked.
- **Rollback:** step-specific; data stays as evidence.

### S9 — Pilot open
- **Founder:** announce to the pilot cohort only.
- **Checkpoint:** daily reconciliation report `OK`, no `dead` outbox rows, no unverified deliveries.

## 3. Stop triggers (any one stops the rollout)

- Any `commerce_webhook.rejected` with `bad_signature` or `unknown_key` from the live site.
- Reconciliation report `ATTENTION` with `paidWithoutActiveGrant`, `activeGrantOnClosedPurchase`, `unverifiedLast24h > 0`, or `unprocessed > 0`.
- A sign-in that creates a second identity for a known account, or any `identity_mismatch` case.
- 5xx on `/auth/bridge/*` or on the webhook beyond a transient retry.
- The ordinary Sejoli login or checkout on `superlatif.id` changes behaviour.

## 4. Daily operation during the pilot

- **Reconciliation report** (read-only; exit code 0 = OK, 2 = ATTENTION):
  ```bash
  DATABASE_URL=<prod> node --experimental-transform-types packages/db/scripts/commerce-reconciliation-report.ts --expect-ref=mfqfkxtrckacrwxltmxg
  ```
  `unboundPurchases` is normal until the buyer signs in. Everything else in `ATTENTION` goes to the support owner.
- **WordPress outbox:**
  ```sql
  SELECT order_id, event_type, status, attempts, last_http_status, last_error FROM <prefix>superlatif_bridge_events WHERE status <> 'delivered' ORDER BY id DESC LIMIT 20;
  ```
  `last_error` says why a delivery failed (1.2.1).
- **Re-send a `dead` event** after fixing its cause: use the `wp eval` replay (§6.2). It sends the stored bytes and event ID, and the app deduplicates.
- **Logs:** Vercel runtime logs are short-lived (about 1 h via CLI). Run the report daily rather than relying on logs; set up a log drain (M5) before scaling past the pilot.

## 5. Decision needed: events from non-pilot products (G5)

Plugin 1.2.x forwards status changes of **every** Sejoli product. With only the pilot product mapped, each order of any other product becomes a purchase in the app with an `unknown_sku` case and no access. That is safe (no access is granted by default) but noisy: the report will show `ATTENTION` all the time. Options:

1. **Accept and filter in the report:** treat `unknown_sku` for known non-pilot product IDs as expected. No code change.
2. **Add a per-client product allowlist to the plugin** (`webhook_products`), so only pilot products are sent. This is a small plugin change with tests, and it needs a new plugin version before S6.
3. **Map every live product.** Needs the full M3 catalogue and content first.

Orders placed **before** activation are not sent (only status changes after S6 are). Existing customers of the pilot product need a separate migration decision (dok 25).

## 6. Command reference (no secrets printed)

### 6.1 Outbound probe from live WordPress (read-only)
```bash
wp eval '$r = wp_remote_post("https://app.superlatif.id/api/v1/integrations/commerce/sejoli_bridge/events", array("timeout"=>10, "redirection"=>0, "body"=>"{}", "headers"=>array("Content-Type"=>"application/json"))); echo is_wp_error($r) ? "WP_Error: " . $r->get_error_code() . " - " . $r->get_error_message() : "HTTP " . wp_remote_retrieve_response_code($r), PHP_EOL;'
```

### 6.2 Replay one delivered or dead outbox row without writing (as used on staging)
```bash
wp eval 'global $wpdb; $t = $wpdb->prefix . "superlatif_bridge_events"; $row = $wpdb->get_row($wpdb->prepare("SELECT event_id, client_id, body FROM {$t} WHERE id = %d", <ROW_ID>), ARRAY_A); $c = superlatif_bridge_commerce_clients()[$row["client_id"]] ?? null; if (!$c) { echo "STOP", PHP_EOL; return; } $r = superlatif_bridge_commerce_send(superlatif_bridge_commerce_url($c), superlatif_bridge_commerce_headers($row["client_id"], $c, $row["event_id"], $row["body"], time()), $row["body"]); echo "HTTP ", $r["status"], " ", $r["error"] ?? "ok", PHP_EOL;'
```

## 7. Full rollback (any point)

Order, fastest first:
1. `FEATURE_COMMERCE_SYNC=false` (webhook 404, claim off).
2. `FEATURE_STUDENT_LOGIN=false` (sign-in off).
3. `PRODUCTION_WRITES_ENABLED=false` if it was opened.
4. Redeploy, or use Vercel Instant Rollback to the pre-activation deployment.
5. On WordPress, remove `webhook_secret` and the client, deactivate the plugin, and reinstall 1.1.0 or remove it.
6. Remove the domain if needed.

There is no migration to roll back. Purchases, grants, and events stay as audit evidence. Grants that must not stand are revoked with a recorded reason, never deleted.
