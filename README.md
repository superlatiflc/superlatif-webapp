# Superlatif Web App

**Versi spesifikasi:** Gates 1–4 Build-Ready RC1/RC2  
**Status implementasi:** P0 governance foundation selesai (`GOV-001`–`GOV-004`); P1 dimulai dengan `IDN-001` (identity, session, deterministic login mapping — schema/migration pertama)  
**Produksi:** `NO_GO` sampai release gate dan external gate lulus

Repository ini berisi source of truth produk, UX, arsitektur, kontrak machine-readable, backlog, fixture sintetis, project instructions, project skills, kerangka monorepo aplikasi, dan (mulai `IDN-001`) domain identity/session pertama dengan schema database sungguhan.

Belum ada route HTTP/API, adapter provider, atau live WordPress/Sejoli bridge. Semuanya dibangun per task backlog, satu per satu.

| Alat    | Versi terkunci                      | Sumber lock                 |

| Node.js | 24.x (dikembangkan pada `v24.15.0`) | `.nvmrc`, `engines`         |


## Setup dari clone bersih

```bash
pnpm install
```

Lalu verifikasi seluruh repository:

```bash
pnpm run verify
```

`verify` menjalankan seluruh pemeriksaan (format → lint → typecheck → build → secret scan → unit → integration → contract → contract-artifact → determinism → migration-drift → starter-bundle) secara berurutan — lihat tabel Script di bawah untuk rincian tiap langkah. Seluruhnya harus hijau.

## Continuous integration

`.github/workflows/ci.yml` menjalankan langkah yang sama dengan `pnpm run verify`, memakai Node dari `.nvmrc` dan pnpm dari `packageManager`, dengan `--frozen-lockfile`.

"Failures block merge" baru benar-benar berlaku setelah workflow ini dijadikan **required status check** pada branch default — itu setelan repository, bukan sesuatu yang bisa dijamin oleh file ini.

## Configuration and secrets (GOV-003)

- `.env.example` adalah satu-satunya sumber nama variabel; `packages/contracts/src/env-spec.ts` mendeklarasikan tipe, tingkat keharusan (`required` / `optional-default` / `optional-no-default`), dan status secret untuk **setiap** variabel — jumlahnya diuji identik dengan `.env.example` (`env.test.ts`).
- `loadCoreEnv()` divalidasi **fail-closed** saat startup (`apps/web/instrumentation.ts`, `apps/worker/src/index.ts`): variabel wajib yang hilang atau tidak valid membuat proses gagal start dengan daftar lengkap pelanggaran, tidak pernah dengan tebakan diam-diam.
- Variabel bertanda `secret: true` tidak pernah memiliki default yang di-hardcode di kode — diperiksa mesin, bukan hanya konvensi.
- Feature flag (`packages/contracts/src/flags.ts`) hanya bisa menjawab hidup/mati (`FeatureFlag.read(): boolean`); tidak ada field yang bisa membawa role/permission/bypass — dibuktikan lewat `@ts-expect-error` di `flags.test.ts`. Flag bukan kontrol otorisasi.
- Kedelapan flag produksi-sensitif (`FEATURE_*`, `SKD_PRODUCTION_ACTIVATION`, `PRODUCTION_WRITES_ENABLED`) default `false` bila tidak diset — diperiksa di dua lapis: `scripts/validate-starter.mjs` (isi `.env.example`) dan `env.test.ts` (skema).
- Secret scanning memakai **Gitleaks 8.30.1**, di-download dan diverifikasi checksum SHA-256-nya sendiri oleh `scripts/install-gitleaks.mjs` (bukan dipercayakan ke Action pihak ketiga) sebelum biner dijalankan. Lihat ADR-044.

## Observability and release evidence (GOV-004)

- `@superlatif/observability` (server/worker only — lihat `packages/observability/src/redaction.ts`, tidak boleh diimpor dari komponen `"use client"`) menyediakan:
  - **correlation ID** (`correlation.ts`) — `AsyncLocalStorage`-based, propagasi terbukti lewat smoke test API → job (worker) → provider dalam satu proses, tanpa dependensi baru.
  - **structured logger** (`logger.ts`) — JSON per baris, level `LOG_LEVEL`-aware, memfilter lewat `redact()` sebelum sampai ke sink. Tidak memilih vendor/exporter (OD-03 tetap terbuka).
  - **redaction** (`redaction.ts`) — denylist diturunkan dari `contracts/analytics-event-catalog.json` + `SECRET_ENV_NAMES`, dengan satu override beralasan (`user_id`, lihat ADR-045) dan default-deny berbasis pola nilai (Bearer/JWT/AWS-key) untuk field yang belum dikenal.
  - **release evidence manifest** (`release-evidence.ts`) — **menolak** (bukan meredaksi) field yang memuat secret/PII/answer payload/webhook mentah; dikunci oleh `releaseId` + `commitSha`.
- `apps/web/src/lib/register-node.ts` dan `apps/worker/src/index.ts` mencatat `startup.config_validated` (sukses) atau `startup.config_invalid` (gagal, `fatal`) lewat logger ini — startup yang sukses maupun gagal sama-sama teramati.
- `scripts/generate-release-evidence.mjs` membangun manifest CI-run (bukan `verify` lokal), diupload sebagai **GitHub Actions artifact** (retensi 90 hari) oleh `ci.yml`. Salinan durable ke repo private `superlatif-ops-evidence` (founder + eng lead, per ADR-042/044) adalah tindakan operator — tidak dibuat atau di-push otomatis oleh kode ini.

## Identity, session, and database (IDN-001)

- **Schema (BD-05, migration pertama)**: `packages/db/src/schema/identity.ts` — `users`, `external_identities`, `user_sessions`, `identity_conflicts`. Sengaja lebih sempit dari `contracts/drizzle-schema.ts`; RBAC (`roles`/`permissions`) milik `IDN-004`, consent/guardian milik task yang belum ditentukan (lihat ADR-046).
- **Merge-key policy** (`packages/domain/src/identity/identity-linking.ts`): `(provider, externalSubject)` adalah **satu-satunya** jalur `link_existing` secara struktural dalam kode — kecocokan email/telepon terhadap user lain hanya bisa menghasilkan `conflict`, tidak pernah auto-link. Diuji tegas di level pure function (`identity-linking.test.ts`) dan level database nyata (`service.integration.test.ts`).
- **Session** (`packages/domain/src/identity/session.ts`): hanya `secret_hash` (SHA-256) yang pernah disimpan; perbandingan `timingSafeEqual`; tidak ada field "session ID yang diberikan caller" di `DeterministicLoginInput` — fixation dicegah oleh bentuk API, bukan sekadar konvensi.
- **Test database**: `packages/db/src/test-client.ts` memakai `@electric-sql/pglite` (WASM Postgres embedded) untuk `test:integration` — cepat, tanpa Docker, tetap menegakkan constraint/FK/unique-index nyata. CI **juga** menjalankan `db:migrate` terhadap **Postgres service container sungguhan** (`postgres:18`, di-pin per digest) untuk parity staging (dok 27 §4).
- **`db:check`** sekarang guard nyata: menjalankan `drizzle-kit generate` dan membandingkan hash isi `packages/db/drizzle/` sebelum/sesudah — gagal kalau schema berubah tapi migration belum di-generate ulang.
- Belum ada route HTTP/API yang memanggil layer ini — `apps/web`/`apps/worker` tidak diubah pada task ini. Wiring HTTP (`/auth/bridge/exchange`, cookie) menyusul di task berikutnya.

## Access grants and entitlement policies (ENT-001)

- **Grant status is derived, never stored**: `access_grants` tidak punya kolom `status`. Perubahan hanya bisa terjadi lewat baris baru di `grant_events` (append-only: `activated | suspended | reinstated | revoked | cancelled`); `packages/domain/src/access/grant-status.ts#deriveGrantStatus` menghitung `scheduled | active | suspended | expired | revoked | cancelled` murni dari `(grant, events, now)` setiap kali dibaca. Lihat ADR-047.
- **Policy versioning**: `access_policies` unik per `(code, version)` — versi baru selalu baris baru, tidak pernah edit di tempat. `config` (JSONB) divalidasi saat runtime terhadap `contracts/entitlement-policy.schema.json` (AJV) sebelum baris manapun ditulis, dan dikunci oleh checksum SHA-256 kanonik (`packages/domain/src/access/policy-checksum.ts`) yang diverifikasi ulang saat `publishPolicyVersion` — config yang berubah di luar API repository ini ditolak sebagai `PolicyChecksumMismatchError`, bukan diam-diam dipublikasikan.
- **Validity modes** (`packages/domain/src/access/policy-validity.ts`): `fixed_window`, `duration_after_purchase`, `duration_after_activation` (menunggu event `activated`), `through_program_or_batch_end` (mensyaratkan `lifecycleEndsAt` eksplisit — belum ada tabel program/batch di scope task ini), `lifetime`, `manual`.
- **Ownership-scoped events**: `recordGrantEvent` menolak event yang `(sourceType, sourceId)`-nya tidak cocok dengan sumber yang menerbitkan grant (`isOwnedBy`), dan mensyaratkan `reason` ketika `lifecycle.manualChangeRequiresReason` true pada policy terkait — grant dari `purchase` tidak bisa direvoke oleh aktor yang mengklaim sebagai `scholarship`.
- **Duplicate content tidak tampil dua kali**: `packages/domain/src/access/dedupe.ts#distinctTargets` mengumpulkan klaim dari sumber berbeda yang menunjuk `(target, action)` yang sama menjadi satu entri, tetap menyimpan seluruh sumber pendukungnya.
- **Test negatif wajib** (`packages/db/src/access/grant-repository.integration.test.ts`): revoked access ditolak, expired access ditolak tepat di batas waktu, grant yang overlap dari sumber berbeda independen satu sama lain (ENT-SYN-002), ownership mismatch ditolak (ENT-SYN-004), duplicate content tidak tampil dua kali.
- **Schema (migration kedua)**: `packages/db/src/schema/access.ts` — `access_policies`, `access_grants`, `grant_events`. Sengaja lebih sempit dari `contracts/drizzle-schema.ts`; `grant_claims`, `effective_access` (materialized view), dan `access_change_requests` milik ENT-002/003/004 (lihat ADR-047).
- Tidak ada bridge WordPress/Sejoli hidup dan tidak ada pembukaan akses dari email semata pada task ini — keduanya di luar scope ENT-001 secara eksplisit.

## Product, offer, SKU, bundle, dan validity policy (COM-001)

- **Immutability diselaraskan dengan ENT-001**: `products` (identitas komersial stabil, `type` bebas teks — Kelas Akselerasi, SKD-only, TKA-only, Tryout Pass, batch flash-sale tunggal cukup jadi nilai `type` baru, bukan migration), `product_versions`, dan `offers` immutable sejak dibuat — checksum SHA-256 kanonik (`packages/domain/src/shared/checksum.ts`, dipromosikan dari ENT-001) di-stamp saat draft, diverifikasi ulang saat `publishProductVersion`/`publishOffer`. "Edit draft" berarti membuat versi N+1, bukan mengubah versi N. Lihat ADR-048 untuk alasan menyimpang dari `checksum` nullable pada `contracts/drizzle-schema.ts`.
- **Bundle tanpa duplikasi konten**: `product_components` menaut `product_version` ke target (`targetType`/`targetRef`/`includeDescendants`) plus `access_policy` (ENT-001) yang membawa aturan validity/attemptAllowance/postExpiry/stacking — komponen tidak pernah menyalin konten. Seluruh component set satu versi dikunci bersama checksum versi itu (tidak bisa ditambah/dihapus setelah dibuat).
- **Komposisi & overlap**: `packages/domain/src/commerce/bundle-composition.ts#composeProductTargets` mengumpulkan klaim komponen — dari satu product version atau lintas product version (bundle + paket spesialis yang overlap) — menjadi target unik; target yang sama dari dua produk berbeda tampil satu kali dengan seluruh source tetap terlihat.
- **Offer sale-state derived, bukan disimpan**: `offers.status` adalah lifecycle editorial (draft/published/archived, sama seperti `access_policies`). Status yang dilihat pembeli (`scheduled | on_sale | sold_out | ended | hidden | archived` — dok 05 §6/dok 18 §4) dihitung oleh `packages/domain/src/commerce/offer-status.ts#deriveOfferSaleState` dari status editorial + visibility + sale window + quota/soldCount setiap kali dibaca — `sold_out` hanya mungkin muncul jika `quota` benar-benar diisi (enforced).
- **SKU mapping berversi**: `external_sku_mappings` adalah baris append-only (`mappingVersion` baru untuk setiap remap). `packages/domain/src/commerce/sku-mapping.ts#resolveSkuMapping` memilih mapping yang berlaku pada satu instant — prioritas lalu mapping version terbaru sebagai tie-break — mendukung ID Sejoli lama & baru dan pemulihan duplicate catalogue entry. Tidak ada webhook atau checkout URL yang dipanggil pada task ini.
- **Test wajib** (`packages/db/src/commerce/*.integration.test.ts`): bundle composition (Kelas Akselerasi membuka banyak target dari satu product version), overlapping product (bundle + paket spesialis sama-sama mencakup `track:skd`, tampil sekali), expired offer, flash sale window (scheduled → on_sale → ended), mapping version test (SKU remap terhadap waktu).
- **Schema (migration ketiga)**: `packages/db/src/schema/commerce.ts` — `products`, `product_versions`, `product_components`, `offers`, `external_sku_mappings`. Sengaja lebih sempit dari `contracts/drizzle-schema.ts`; `checkout_intents`, `purchases`, `purchase_events`, `reconciliation_cases` milik COM-002/COM-003 (lihat ADR-048).
- Tidak ada checkout/live Sejoli bridge dan tidak menyentuh payment provider pada task ini — keduanya di luar scope COM-001 secara eksplisit.

## RBAC dan object-level authorization (IDN-004)

- **Delapan role kanonik** (dok 02 §5.3/dok 21 §3/dok 24 §6, sama persis dengan `CLAUDE.md`): `super_admin`, `operations_admin`, `academic_admin`, `tutor_writer`, `moderator_reviewer`, `live_class_coordinator`, `support`, `finance_reconciliation`. Instruksi founder memakai istilah lebih sederhana ("student, admin, tutor, moderator, owner/founder") — pemetaannya (student = tanpa role sama sekali; tutor→`tutor_writer`; moderator→`moderator_reviewer`; owner/founder→`super_admin`) didokumentasikan di `packages/domain/src/authorization/roles.ts` dan ADR-049.
- **Permission matrix versioned di kode, bukan tabel runtime-editable**: `packages/domain/src/authorization/permissions.ts#ROLE_PERMISSION_MATRIX` transkripsi langsung dari matriks dok 24 §6, default-deny (permission yang tidak tercantum = ditolak). `permissions`/`role_permissions` sengaja tidak dibuat sebagai tabel DB — belum ada admin UI untuk mengeditnya (di luar scope task ini).
- **Object-level check tiga sumbu independen** (`packages/domain/src/authorization/object-scope.ts`): `isOwner` (kepemilikan), `isWithinAssignedScope` (scope role — array assignment kosong berarti unscoped), `isEntitled` (entitlement, sebuah boolean yang dihitung caller dengan mengompos ENT-001's `deriveGrantStatus`, bukan dihitung di dalam domain authorization). Dikomposisi oleh `packages/domain/src/authorization/authorize.ts#authorize` — fungsi murni, tanpa I/O.
- **Maker-checker bersifat universal**: `authorize()` menolak `MAKER_CHECKER_VIOLATION` setiap kali `object.creatorUserId === actor.userId`, terlepas dari role — bahkan `super_admin` tidak bisa approve soal buatannya sendiri.
- **Privileged mutation tidak bisa melewati audit trail**: aksi `highRiskType` (dok 24 §7) ditolak `AUDIT_FIELDS_REQUIRED` bila `reason`/`correlationId`/`actorId` kosong — ditegakkan di dua lapis: `authorize()` (domain) dan `packages/db/src/authorization/role-repository.ts#assignRole`/`revokeRoleAssignment` (DB, `RoleAssignmentAuditRequiredError`).
- **Schema (migration keempat)**: `packages/db/src/schema/authorization.ts` — `roles`, `user_roles` (immutable sejak dibuat, sama seperti `access_grants`), `role_assignment_scopes` (tabel assignment terpisah untuk scope, sesuai dok 21 §3), `role_assignment_events` (append-only `revoked`/`reinstated`; status derived, tidak disimpan).
- **Test negatif wajib** (`packages/domain/src/authorization/authorize.test.ts`, `packages/db/src/authorization/role-repository.integration.test.ts`): siswa membaca attempt siswa lain (SEC-SYN-001), tutor di luar scope program, moderator mengubah entitlement, admin melewati audit trail — plus SEC-SYN-002/003/004 dari `test/fixtures/contracts/privacy-rbac.cases.json`.
- Tidak ada bridge WordPress/Sejoli hidup, tidak ada UI admin, dan tidak ada akses berbasis email semata pada task ini — ketiganya di luar scope IDN-004 secara eksplisit. Lihat ADR-049.

## Effective-access resolver, cache, dan explanation trace (ENT-002)

- **Tidak ada migration baru**: resolver membaca apa yang sudah disimpan ENT-001 (`access_grants`, `grant_events`, `access_policies.config.claims`) — `grant_claims` dan `effective_access` (materialized/rebuildable) sengaja tidak dibuat di task ini; tidak ada consumer nyata untuk `grant_claims`, dan rebuild/drift detection untuk `effective_access` adalah scope ENT-003. Lihat ADR-050.
- **Resolver mengembalikan keputusan + explanation, bukan boolean**: `packages/domain/src/access/effective-access.ts#resolveEffectiveAccess` selalu mengembalikan `{allowed, decisiveGrantIds, ignoredGrantIds, reasonCode, effectiveFrom, effectiveTo, studentReason, diagnostic}` (dok 05 §9) — fungsi murni, dikompos dari daftar grant yang statusnya sudah di-derive lewat `deriveGrantStatus` (ENT-001).
- **Duplicate target tidak tampil dua kali**: dua grant aktif yang sama-sama meng-claim target/action yang sama menghasilkan **satu** keputusan dengan `decisiveGrantIds` berisi keduanya — bukan dua keputusan terpisah. `effectiveTo` mengikuti `expiryResolution=latest_supporting_grant` (akhir terjauh di antara grant aktif yang mendukung).
- **Revoked/expired/suspended/cancelled ditolak dengan explanation trace jelas**: setiap grant yang meng-claim target tapi tidak decisive muncul di `ignoredGrantIds` plus `diagnostic` (status derived tiap grant) — support tetap bisa melihat semua sumber, bukan hanya yang menang.
- **Attempt allowance terpisah dari content visibility (ENT-005)**: `packages/domain/src/access/attempt-allowance.ts#resolveAttemptAllowance` adalah fungsi **terpisah**, tidak pernah digabung ke `EffectiveAccessDecision` — default MVP `ownedByBatch:true` (batch adalah satu-satunya pemilik limit) sesuai dok 05 §8.4, tidak pernah mengarang angka.
- **Cache in-process, mudah diganti**: `EffectiveAccessCache` (`packages/domain/src/access/effective-access-cache.ts`) adalah interface tiga method; `createInMemoryEffectiveAccessCache` (Map-based, `now` di-inject, tanpa `Date.now()`) satu-satunya implementasi — tidak ada Redis/Valkey. Invalidasi hanya lewat `issueGrantAndInvalidate`/`recordGrantEventAndInvalidate` (`packages/db/src/access/effective-access-service.ts`), yang membungkus `issueGrant`/`recordGrantEvent` ENT-001 tanpa mengubahnya.
- **`includeDescendants` tetap butuh ancestry dari caller**: sama seperti `lifecycleEndsAt` di ENT-001, `isDescendantOf` adalah parameter opsional yang harus disuplai caller — belum ada tabel hierarki program/track (PRG series).
- **Gate A tidak diklaim PASS**: task ini hanya melengkapi ENT-003/004/005 requirement; `planning/release-gates.json` tidak diubah — status gate tetap keputusan founder/owner terhadap requirement set lengkap. Lihat ADR-050.

## Manual grant, extension, dan revocation dengan reasoned approval (ENT-004)

- **Dua tabel append-only, bukan satu row berstatus mutable**: `access_change_requests` (ask immutable — changeType, target, requester, reason, correlationId, payload, previewSnapshot) + `access_change_decisions` (append-only — approve/reject plus hasil eksekusi). Status (`pending_approval|rejected|executed|execution_failed`) di-derive lewat `packages/domain/src/access/manual-change.ts#deriveManualChangeStatus`, tidak pernah disimpan. Lihat ADR-051.
- **Preview adalah before-state nyata**: `requestManualChange` menghitung `previewSnapshot` — effective access SEBELUM perubahan untuk setiap target/action yang di-cover policy yang diminta (lewat ENT-002's `getEffectiveAccess`) — dihitung sekali saat request, disimpan verbatim.
- **`authorize()` (IDN-004) menggerbangi setiap langkah**: `requestManualChange` menolak sebelum menulis apa pun bila actor tidak punya `access.manual.change` atau `reason`/`correlationId` kosong (`AUDIT_FIELDS_REQUIRED`, action type `manual_grant_revoke_extension` — high-risk per dok 24 §7). `decideManualChange` memanggil `authorize()` lagi untuk approver, dengan `object.creatorUserId = requester` — self-approval ditolak `MAKER_CHECKER_VIOLATION` secara struktural, berlaku untuk semua role.
- **Melengkapi nuance IDN-004 yang sengaja ditunda**: `access.manual.change` untuk `academic_admin`/`operations_admin` dinaikkan dari `scoped_nuance` ke `granted` (`requiresApproval:true`) — "Terbatas" sekarang berarti "wajib peer approval", ditegakkan universal oleh workflow ini, bukan oleh flag matrix per role. `support`'s "Request terbatas" sengaja tetap belum diselesaikan (request-only, di luar scope task ini).
- **Manual grant memakai `sourceId` stabil per-siswa**: setiap manual grant memakai `sourceId=targetUserId` (bukan id request) + `sourceKey=changeRequestId` — membuat revocation manual TERHADAP GRANT MANUAL manapun untuk siswa itu selalu bisa (ownership match), sekaligus membuat revocation manual terhadap grant **purchase** gagal secara struktural (`GrantOwnershipMismatchError`, `"manual" !== "purchase"`) — inilah yang menegakkan "jangan pernah rewrite purchase grant asli" pada level eksekusi, bukan hanya konvensi.
- **Kegagalan eksekusi tidak melempar exception mentah**: bila approval disetujui tapi eksekusi gagal (mis. ownership mismatch), decision tetap tercatat dengan `executionStatus:"execution_failed"` — keputusan manusia tetap teraudit, mutasi tidak pernah terjadi.
- **Cache invalidation diwarisi, bukan diimplementasi ulang**: eksekusi hanya memanggil `issueGrantAndInvalidate`/`recordGrantEventAndInvalidate` (ENT-002) — satu-satunya fungsi yang menyentuh cache di seluruh codebase.
- **Test negatif wajib** (`packages/db/src/access/manual-change-service.integration.test.ts`): unauthorized actor, missing reason, self-approval, revoking purchase grant by mutation, stale effective access cache — semua lulus lewat DB nyata.
- Tidak ada UI admin dan tidak ada WordPress/Sejoli bridge pada task ini — keduanya di luar scope ENT-004 secara eksplisit.

## Program-centric home, active context, dan cross-product dedup (PRG-001)

## Reusable learning resources, asset, recording, dan secure delivery (LRN-001)

- **Schema baru mengisi celah `assets` yang sengaja ditinggalkan PRG-002**: `assets` (satu file/stream milik satu `resource_version`, `role`-keyed sehingga satu version bisa punya lebih dari satu asset — video utama + caption — tanpa rantai asset-di-dalam-asset), `recordings` (lifecycle `pending → processing → ready/failed → archived` persis dok 14 §14, independen dari status draft/published/archived resource version-nya sendiri), `asset_delivery_references` (token yang benar-benar diterbitkan). `resource_versions` tetap tanpa `primaryAssetId` — kepemilikan berjalan arah sebaliknya (`assets.resourceVersionId`), sehingga masalah FK sirkular tidak pernah muncul.
- **`storageRef` opaque end-to-end, ditegakkan secara struktural**: string sintetis berbentuk seperti key object-storage nyata, tapi tidak pernah di-resolve ke provider nyata di manapun pada task ini. Hanya dibaca di SATU tempat di seluruh codebase — langkah terakhir `resolveAssetDelivery` yang server-only — tidak pernah oleh `requestAssetDelivery` (fungsi yang dipanggil caller student-facing). Test "no raw asset URL leak" menegaskan ini langsung.
- **Secure delivery = DUA pemeriksaan, bukan satu**: `requestAssetDelivery` (saat request) memakai `assertProgramAccess` (ENT-002/IDN-004, tidak diubah) plus `resolvePlacementVisibility` baru (`@superlatif/domain/program`) yang meng-AND-kan release rule placement sendiri dengan visibility modul induknya. `resolveAssetDelivery` (saat redeem) TIDAK mempercayai bahwa reference tadi valid saat diterbitkan — ia menjalankan ulang `assertProgramAccess` secara FRESH, plus memeriksa TTL — inilah dok 14 §14 "access mengikuti grant saat playback, bukan hanya saat link dibuat" secara operasional: reference yang belum kadaluarsa TTL-nya tetap ditolak jika grant yang mengizinkannya sudah dicabut di antara waktu penerbitan dan redeem.
- **Expiry di-cap oleh grant, bukan cuma TTL**: `expiresAt` reference = `min(now + ttlSeconds, effectiveAccessDecision.effectiveTo)` (`computeDeliveryExpiry`) — reference tidak pernah bisa hidup lebih lama dari grant yang mengizinkannya.
- **Hanya hash yang disimpan**: `asset_delivery_references.tokenHash` — tidak ada kolom token mentah, persis disiplin `userSessions.secretHash` (IDN-001). `secure-delivery.ts` sengaja TIDAK mengimpor ulang `identity/session.ts` — kelas kredensial berbeda, generator harus independen.
- **Reuse tanpa duplikasi berlaku by construction**: asset dimiliki oleh `resource_version`, bukan `resourcePlacements` — resource yang sama dipasang di dua program berbeda tetap resolve ke `storageRef` yang identik, hanya satu baris asset yang pernah dibuat.
- **Rekaman metadata-only, tidak ada provider call**: `recordings.sourceKind = "provider"` menyimpan `providerRef` sebagai referensi opaque yang tidak pernah di-dereference ke provider nyata di task ini.
- **Test wajib** (`packages/domain/src/program/secure-delivery.test.ts`, `packages/domain/src/program/release-rule.test.ts` — `resolvePlacementVisibility`, `packages/db/src/program/delivery-service.integration.test.ts`): authorized delivery, expired signed reference, expiry di-cap oleh grant, unauthorized access (request-time dan revoked-antara-issue-dan-redeem), reusable resource lintas dua program, recording metadata (pending → ready), no raw asset URL leak — seluruhnya lulus lewat DB nyata (pglite).
- Tidak mengklaim Gate B atau Gate D PASS. Tidak ada integrasi S3/CDN/video provider nyata, tidak ada admin UI, tidak ada route download/stream proxy di `apps/web` pada task ini. Lihat ADR-054.

## Raw commerce event ingestion dan provider payload normalization (COM-002)

- **Schema mengisi celah `purchases`/`purchase_events` yang sengaja ditinggalkan COM-001**: `raw_commerce_events` (envelope immutable — provider, site, `eventKey`, `signatureOutcome`, `payloadChecksum`, payload ter-redaksi, `receivedAt`, `correlationId`), `commerce_event_quarantine` (satu baris per event yang gagal dinormalisasi — bukan log line), `normalized_commerce_events` (bentuk kanonis dok 22 §17, provider-agnostic, siap dipakai COM-003). `purchase_state` adalah enum baru yang mentranskripsi persis vocabulary "Purchase states" canonical CLAUDE.md — task ini yang pertama benar-benar menyimpannya.
- **Tanpa koneksi Sejoli/WordPress live, tanpa secret production**: `@superlatif/domain/commerce/webhook-verification.ts` mengimplementasikan HMAC-SHA256 + timing-safe compare (dok 23 §8) sebagai fungsi murni; secret SELALU parameter yang di-inject caller, tidak pernah dibaca dari env — tidak ada entri `.env.example` baru untuk secret webhook, sengaja, karena OD-01/OD-02 masih terbuka. `secret === null` menghasilkan `"unverified"` — outcome berbeda dari `"failed"`, tetap disimpan, tetap quarantine-worthy.

- **Redaksi defense-in-depth**: `redactRawPayload` menghapus nilai key yang berbentuk credential (`password`/`secret`/`token`/`card`/`cvv`/`account_number`/`api_key`/`authorization`) secara rekursif — tidak percaya begitu saja pada klaim dok 23 §7 bahwa bridge sudah meredaksi. `payloadChecksum` dihitung dari payload ASLI sebelum redaksi (SHA-256 satu arah, tidak bisa bocorkan secret).
- **Idempotency di-cek sebelum transaksi dibuka**: `deriveEventKey` memilih ID stabil dari provider atau fallback checksum kanonis. `ingestCommerceEvent` mengembalikan `{kind:"duplicate"}` tanpa menulis apa pun untuk `(provider, eventKey)` yang sudah pernah masuk — dibuktikan lewat test yang memverifikasi tepat satu baris raw event untuk key yang sama.

Test negatif memanggil fungsi ini langsung dan memverifikasi `rawPayloadRedacted`/`payloadChecksum` tidak berubah.
- **Pipeline sinkron — simplifikasi terdokumentasi, bukan klaim bentuk produksi**: belum ada infrastruktur queue/worker-dispatch di repository ini, jadi `ingestCommerceEvent` menjalankan persist → verify → normalize/quarantine secara sinkron dalam satu transaksi. Task queue-backed di masa depan bisa memanggil fungsi yang sama tanpa mengubah kontraknya.
- **Test wajib** (`packages/domain/src/commerce/webhook-verification.test.ts`, `canonical-event.test.ts`, `payload-redaction.test.ts`, `packages/db/src/commerce/commerce-event-service.integration.test.ts`): valid event normalization, invalid signature rejection, unknown event quarantine (unsupported type & unrecognized status), duplicate/idempotency, no raw payload mutation — seluruhnya lulus lewat DB nyata (pglite), fixture fabricated-but-realistic.

## Purchase lifecycle menjadi access grant, dengan outbox delivery (COM-003)

- **Schema mengisi `purchases`/`purchase_events`/`reconciliation_cases` dok 21 §4, plus `commerce_outbox` (bukan dari dok 21, minimal, bukan full queue)**: `purchases` adalah SATU-SATUNYA proyeksi mutable dalam write-set task ini ("upsert purchase snapshot", dok 23 §11) — fact log-nya tetap `purchase_events` (append-only) plus `access_grants`/`grant_events` (ENT-001, tidak diubah sama sekali). `reconciliation_cases` sengaja terpisah dari `commerce_event_quarantine` COM-002: quarantine untuk event yang gagal DINORMALISASI, reconciliation case untuk event ternormalisasi yang gagal DIPROSES (unknown SKU, unresolved identity, transisi ambigu, partial refund tak terverifikasi, policy validity tak terselesaikan, chargeback review).
- **Transition legality = resolver murni, data-driven**: `@superlatif/domain/commerce/purchase-transition.ts#resolvePurchaseTransition` mengecek staleness dulu (occurredAt lebih awal dari state saat ini → ditolak apa pun status targetnya), lalu legality (`ALLOWED_TRANSITIONS`, tabel data, bukan switch statement). `paid → pending` sengaja tidak ada di tabel (dok 22 §18) — bahkan dengan timestamp lebih baru. State terminal (`expired`/`cancelled`/`refunded_full`/`chargeback`) tidak punya edge keluar sama sekali.
- **Dua lapis idempotency independen**: (1) `purchase_events.normalizedEventId` unique — replay event ternormalisasi yang sama mengembalikan outcome tersimpan, bukan diproses ulang. (2) `access_grants` (userId, sourceType, sourceKey) milik ENT-001 sendiri — `sourceType="purchase"`, `sourceId=purchase.id` (dipakai bersama semua grant dari satu purchase, sehingga refund/cancel bisa temukan & cabut tepat grant purchase ini), `sourceKey="${purchase.id}:${componentCode}"` (satu grant per komponen produk, replay-safe). Provider retry dengan delivery ID beda tapi status sama ditangkap lapis kedua sebagai `"duplicate"`, bukan lapis pertama — dibuktikan test terpisah.
- **Grant issuance/revocation memakai ENT-001/ENT-002 apa adanya, tanpa kode mutasi grant baru**: `paid` menerbitkan satu grant per `productComponents` (offer yang sudah di-resolve dari SKU mapping COM-001), pakai `computeValidityWindow` per komponen — policy `through_program_or_batch_end` tanpa lifecycle table degradasi jadi reconciliation case HANYA untuk komponen itu, tidak membatalkan seluruh purchase. `refunded_full`/`cancelled` mencabut (`"revoked"`) hanya grant milik purchase ini (filter sourceType+sourceId), grant lain tetap utuh. `chargeback` men-suspend (`"suspended"`, bukan revoke — dok 22 §18: tidak menuduh siswa curang) plus reconciliation case review. `refunded_partial` TIDAK ada aksi otomatis sama sekali — task ini tidak punya granularity line-item untuk memverifikasi nominal (dok 22 §18), jadi selalu menjadi reconciliation case.
- **Outbox atomicity dibuktikan langsung terhadap failure mode nyata**: test wajib membuka transaksi manual, menerbitkan grant sungguhan, lalu sengaja menulis baris outbox dengan `purchaseId` yang tidak ada (melanggar FK) untuk memaksa gagal — memverifikasi grant tadi TIDAK ada setelah rollback. `drainCommerceOutbox` adalah fungsi sinkron dengan consumer yang di-inject (`publish`), bukan queue worker — kegagalan `publish` meninggalkan baris `pending` untuk drain berikutnya, tidak memblokir baris lain.
- **Test wajib** (`packages/domain/src/commerce/purchase-transition.test.ts`, `packages/db/src/commerce/purchase-lifecycle-service.integration.test.ts`): paid creates grant once, duplicate/replay (event sama & provider retry beda delivery ID), refund revokes access (grant asli tidak pernah ditulis ulang), out-of-order event (paid→pending ditolak, reconciliation case dibuat), unknown SKU & unresolved identity (purchase tetap dibuat, reconciliation case, tanpa grant), outbox prevents partial commits — seluruhnya lulus lewat DB nyata (pglite), diproses lewat pipeline `ingestCommerceEvent` COM-002 yang sungguhan, bukan shortcut.
- Tidak mengklaim Gate A atau Gate D PASS karena OD-01 masih terbuka. Tidak ada route `apps/web` yang memanggil `processPurchaseLifecycleEvent` otomatis, tidak ada resolusi checkout-intent (belum ada alur checkout), tidak ada notifikasi nyata terkirim (outbox hanya mencatat kewajiban). Lihat ADR-056.

## Refund, cancellation, expiry, dan source-isolated revocation (COM-004)

- **Tidak ada schema baru, tidak ada production code baru**: seluruh acceptance COM-004 sudah terpenuhi oleh mekanisme COM-003 + ENT-001/ENT-002 yang ada — `applyPurchaseStatusEffects` sudah memfilter revocation ke `sourceType === "purchase" && sourceId === purchase.id`, dan `recordGrantEvent` (ENT-001) sudah mewajibkan `reason` untuk event revoked/suspended/cancelled/reinstated. Write-set task ini HANYA satu file test integration baru, membuktikan mekanisme yang sudah ada terhadap skenario multi-source yang lebih keras, bukan menambah mekanisme baru.
- **Overlapping-grant refund dibuktikan di layer yang dilihat siswa, bukan cuma baris tabel**: dua grant independen untuk target yang SAMA (`program:aks-2026`) dari dua purchase berbeda (bundle + specialist) — refund purchase specialist SAJA, verifikasi grant bundle tidak tersentuh (tidak ada event `revoked`, row sama) DAN `getEffectiveAccess` untuk target itu tetap `allowed: true` lewat grant bundle yang bertahan.
- **Unknown-source revocation denial diperluas lintas TIPE source, bukan cuma purchase lain**: grant manual (`sourceType="manual"`, konvensi ENT-004) untuk target yang sama seperti grant purchase — refund purchase-nya, grant manual dipastikan tidak tersentuh sama sekali, akses tetap ada lewat grant manual itu.
- **Expiry boundary = purchase-lifecycle state, bukan grant-lifecycle**: `pending → expired` (window pembayaran habis) tidak pernah menerbitkan grant sama sekali — beda dari grant `validTo` yang sudah otomatis ditangani ENT-001/ENT-002 tanpa keterlibatan commerce sama sekali.
- **Idempotent repeated refund/cancel dibuktikan langsung terhadap audit trail**: dua delivery BERBEDA (eventId beda, simulasi provider retry) yang sama-sama melapor `refunded_full` — delivery kedua ditangkap `resolvePurchaseTransition` sebagai `"duplicate"` sebelum kode grant jalan; test menghitung baris `grant_events` langsung: tepat satu `"revoked"`, bukan dua.
- **Test wajib** (`packages/db/src/commerce/source-isolated-revocation.integration.test.ts`, 7 test): overlapping-grant refund, unknown-source revocation denial, cancellation (paid→cancelled dan pending→cancelled no-op), expiry boundary + idempotent replay, idempotent repeated refund, reason-required audit trail (refund/cancel/chargeback semuanya punya reason yang benar) — seluruhnya lulus lewat DB nyata (pglite), diproses lewat pipeline `ingestCommerceEvent` COM-002 yang sungguhan.
- Tidak mengklaim Gate A atau Gate D PASS karena OD-01 masih terbuka. Tidak ada perubahan schema, tidak ada migration baru — `db:check` tidak punya apa pun untuk dilaporkan. Lihat ADR-057.

## Commerce reconciliation dan exception operations (COM-006)

- **Tidak ada tabel baru — empat kolom nullable di `reconciliation_cases`**: `assignedToUserId`, `resolvedByUserId`, `resolvedAt`, `resolutionReason`. Repair `unknown_sku`/`unresolved_identity` me-resolve ulang blocker asli (`resolveOfferForSku`/`findExternalIdentity`, tidak berubah), lalu memanggil fungsi yang sama; repair `chargeback_review` memanggil `recordGrantEventAndInvalidate` (ENT-001/ENT-002) langsung, persis seperti jalur chargeback COM-003 sendiri.

Tidak mengklaim production sign-off — finance-approved evidence belum ada (stop condition task ini sendiri). Tidak ada koneksi Sejoli/WordPress live. Fungsi reconciliation summary/report (dok 25 §12 "Counts") sengaja ditunda — required test tidak membutuhkannya. Lihat ADR-058.

## Deterministic entitlement rebuild dan drift detection (ENT-003)

- **Tidak ada schema baru — "rebuild" sudah ada, tinggal diberi nama**: `getEffectiveAccess` (ENT-002) pada cache miss sudah melakukan tepat dua hal — ambil semua grant dari source records (`listResolvableGrantsForUser`) lalu hitung ulang decision (`resolveEffectiveAccess`), keduanya murni/tidak berubah. `rebuildEffectiveAccess` adalah pasangan panggilan yang sama, diberi nama sendiri supaya bisa diminta eksplisit, bukan cuma terjadi kebetulan saat cache miss.
- **Dua drift check independen, karena dua kelas masalah berbeda dengan respons benar yang berbeda**: `detectEffectiveAccessDrift` (cache vs rebuild) SELF-HEALING — satu-satunya tindakan benar adalah `cache.invalidateUser` (metode ENT-002 sendiri, sudah dipakai `issueGrantAndInvalidate`/`recordGrantEventAndInvalidate`) — tidak ada reconciliation case karena tidak ada keputusan yang perlu manusia ambil. `detectPurchaseGrantDrift` (paid purchase vs supporting grant) BUKAN self-healing — purchase paid tanpa grant sama sekali bisa jadi bug nyata atau exception yang sudah didokumentasikan (dok 05 §14 / dok 25 §12) — selalu membuat baris `reconciliation_cases` COM-006 (case type baru `paid_purchase_no_grant`, ditambahkan ke union free-text yang sudah ada — nol dampak schema) untuk direview manusia, diselesaikan lewat `resolveReconciliationCase` COM-006 yang sama persis.
- **"Repair" tidak pernah melebarkan akses — dibuktikan secara arah, bukan cuma ketiadaan kode pelebar**: `compareEffectiveAccessDecisions` melaporkan ARAH ketidaksesuaian — `cache_over_permissive` (cache bilang boleh, rebuild bilang tidak — arah berbahaya dok 05 §16 invariant 8) vs `cache_under_permissive` (arah aman — grant nyata ada tapi cache belum tahu). Test "no access widening" wajib menjalankan urutan sungguhan (isi cache saat allowed, cabut grant di luar jalur invalidasi, deteksi drift, invalidate, baca ulang) dan memverifikasi hasil baca ulang adalah decision REBUILT yang lebih restriktif, bukan cache lama yang permisif.
- **Non-determinisme laten ditemukan dan diperbaiki**: `listGrantsForUser` (ENT-001) ternyata tidak punya `ORDER BY` sama sekali — `decisiveGrantIds` diturunkan langsung dari urutan array pemanggilnya (dedupe, tidak pernah disortir), jadi fetch tanpa urutan bisa melaporkan grant overlapping yang sama dalam urutan berbeda antar-panggilan, murni artefak penyimpanan fisik, bukan perubahan entitlement nyata. Diperbaiki dengan `.orderBy(asc(createdAt), asc(id))` — perubahan minimal, murni additive (tidak ada perubahan semantik, hanya jaminan determinisme).
- **Test wajib** (`packages/domain/src/access/entitlement-drift.test.ts`, `packages/db/src/access/entitlement-rebuild-service.integration.test.ts`, 13 test total): repeatable rebuild, drift detection + stale cache detection (revoke grant di luar jalur invalidasi, cache tetap stale sampai drift detection menangkapnya), no access widening (dua skenario: baca ulang setelah repair, dan no-drift-when-agree), deterministic output ordering (tiga grant overlapping dari tiga source berbeda, lima rebuild berulang, urutan `decisiveGrantIds` identik), repair audit (reconciliation case dibuat, idempotent pada deteksi ulang, manusia menyelesaikan dengan audit trail lengkap) — seluruhnya lulus lewat DB nyata (pglite).
- Tidak mengklaim Gate A atau Gate D PASS. Tidak ada koneksi Sejoli/WordPress live. `paid_purchase_no_grant` TIDAK PERNAH diperbaiki otomatis dengan menerbitkan grant — selalu keputusan manusia, reuse alur manual ENT-004 kalau memang grant seharusnya ada. Lihat ADR-059.

## Schedule, live class, reminder, recording, dan attendance lifecycle (SCH-001)

- **Schema mentranskripsi dok 14 §11 apa adanya**: `schedule_item_type` dan `live_session_status` (enum tertutup, sama disiplin dengan `grantEventType`/`recordingProcessingStatus`), `schedule_items` (program/track + timezone eksplisit), `live_sessions` (`provider`/`externalMeetingRef` opaque, tidak pernah di-resolve ke provider nyata), plus `live_session_join_references`, `live_session_attendance`, `live_session_reminders`.
- **Join-link security = model dua-check LRN-001, dipakai ulang di level primitif, bukan diduplikasi di level tabel**: `requestLiveSessionJoin`/`resolveLiveSessionJoin` meniru `requestAssetDelivery`/`resolveAssetDelivery` persis, memakai ulang crypto primitives `@superlatif/domain/program` (`generateDeliveryToken`/`hashDeliveryToken`/`computeDeliveryExpiry`/dst) TANPA PERUBAHAN — nol kriptografi baru. `live_session_join_references` tabel BARU (bukan reuse `asset_delivery_references`) karena target FK memang beda (session, bukan asset+placement) — instruksi "jangan bikin write path baru" dipenuhi di level yang penting (nol implementasi kedua untuk logika token keamanan), bukan dengan memaksakan FK tabel yang tidak cocok. Urutan dok 14 §12 diikuti persis: akses dievaluasi SEBELUM window/status.
- **Recording reuse LRN-001 tanpa perubahan**: `linkRecording` hanya SATU `UPDATE live_sessions SET recording_id = ...` — task ini tidak mendefinisikan vocabulary `sourceKind`/`processingStatus`/`providerRef` sendiri sama sekali; pembuatan recording tetap sepenuhnya kode LRN-001 yang sudah ada.
- **Reschedule append-only**, persis dok 14 §13: row LAMA ditandai `status="rescheduled"` (status yang tidak joinable) dan startsAt/endsAt aslinya tetap permanen; row BARU dibuat dengan `rescheduledFromId` menunjuk yang lama. `rescheduledFromId` sengaja tanpa FK constraint — sama seperti `offers.upgradeFromOfferId` (COM-001).
- **Reminder = model sintetis, bukan full notification lifecycle dok 19 §12**: status hanya `planned`/`cancelled` dalam task ini — lifecycle penuh (`queued`/`provider_accepted`/`delivered`/dst) adalah scope NTF-001 (sudah di backlog, dependsOn SCH-001). Reschedule/cancel membatalkan reminder pending; reminder baru untuk occurrence baru adalah panggilan eksplisit caller sendiri (`scheduleReminder`), tidak otomatis.
- **Otorisasi tidak butuh perubahan `permissions.ts` sama sekali**: `live.occurrence.manage` sudah `granted` untuk `academic_admin`/`operations_admin`/`live_class_coordinator` di matriks IDN-004 — persis kebutuhan task ini.
- **Test wajib** (`packages/domain/src/program/schedule.test.ts`, `packages/db/src/program/schedule-service.integration.test.ts`, 20 test total): authorized join link, unauthorized access denied (+ access revoked antara issue-redeem), no raw provider join URL leak, attendance check-in/out (idempotent), recording linked to session, reminder scheduled, cancelled/rescheduled session (append-only, reason wajib, reminder lama dibatalkan, join ke occurrence lama ditolak), timezone boundary — seluruhnya lulus lewat DB nyata (pglite).
- Tidak mengklaim Gate B PASS. Tidak ada integrasi Zoom/Google Meet/provider video nyata, tidak ada WhatsApp/email reminder nyata, tidak ada route `apps/web`. Lihat ADR-060.

## Versioned question bank: questions, stimuli, options, assets, dan answer secrets (QST-001)

- **Schema mentranskripsi dok 15 §4/dok 21 §8 apa adanya**: enum `question_type` tertutup (`single_choice`/`multiple_choice`/`true_false`/`weighted_choice`/`numeric`); `questions`/`question_versions` dan `stimuli`/`stimulus_versions` memakai split identity/version yang sudah baku (ENT-001/COM-001/PRG-002); `question_options` RELASIONAL (bukan JSONB) karena `optionCode` harus jadi key stabil yang dirujuk `question_assets` maupun bentuk answer key; untuk `type="true_false"`, baris option merepresentasikan STATEMENT. `classification` (JSONB versioned config, bukan tabel referensi baru) dan `explanationDocument` (bukan secret — bagian editor manual dok 15 §6 yang terpisah dari answer/scoring metadata) ada langsung di `question_versions`.
- **`question_version_secrets` = security boundary, dijaga dua lapis**: relasional (tabel terpisah 1:1, hanya `question-secret-repository.ts` yang pernah membacanya) DAN struktural (`toStudentFacingQuestionView`'s input type — `student-view.ts` — tidak punya field yang bisa diisi `AnswerKey` sama sekali, jadi kebocoran adalah type error, bukan celah disiplin). `weighted_choice` memakai satu fungsi pure `toStudentResponseKind` untuk aturan CLAUDE.md "student response shape kind=single_choice + optionCode" — `type` internal tetap `"weighted_choice"` untuk scoring, hanya `responseKind` yang pernah melapor `"single_choice"`. `assertValidAnswerKey` menegakkan seluruh aturan kelengkapan dok 15 §6 per tipe (termasuk menolak invalid option key) sebelum baris secret ditulis.
- **Aturan mutability sengaja BERBEDA dari pola "immutable sejak dibuat" (ENT-001/COM-001/PRG-002)**: dok 15 §4 eksplisit — draft/in_review/changes_requested boleh diedit di tempat; hanya approved/published/archived yang terkunci (`isQuestionVersionLocked`/`assertQuestionVersionMutable`, dipakai ulang tanpa modifikasi untuk `stimulus_versions`). Checksum diverifikasi ulang sebelum setiap transisi ke status terkunci (disiplin yang sama dengan `policy-repository.ts#publishPolicyVersion`), dan `lockedAt` di-stamp sekali saja pada transisi pertama ke status terkunci.
- **`question_assets` tabel BARU, bukan retrofit `assets` (LRN-001)**: pola opaque `storageRef` dipakai ulang (tidak pernah di-resolve ke provider object-storage/CDN nyata), tapi `resourceVersionId` LRN-001 adalah konsep kurikulum yang tidak relevan untuk question/stimulus version — pilihan yang sama dengan `live_session_join_references` (SCH-001). Owner XOR (`questionVersionId` XOR `stimulusVersionId`) ditegakkan di application layer, sama seperti presedan `reconciliation_cases` (COM-003/COM-006). Asset dengan `placement="option"` wajib merujuk `optionCode` yang benar-benar ada pada version tersebut.
- **Otorisasi tidak butuh perubahan `permissions.ts` sama sekali**: `question.draft.write`/`question.first_approve`/`question.ranked_publish` sudah ada di matriks IDN-004 — `question.first_approve`'s `requiresNonCreator: true` membuat `authorize()` menolak penulis menyetujui draft sendiri (`MAKER_CHECKER_VIOLATION`), persis CLAUDE.md "creator, first approver, dan second approver harus beda actor".
- **Tidak ada JSON Schema contract baru** — divalidasi fungsi TypeScript murni di `@superlatif/domain/exam`, sama pendekatan PRG-002/LRN-001/SCH-001 untuk field JSONB mereka sendiri.
- **Test wajib** (`packages/domain/src/exam/*.test.ts` 31 test — answer-key validation per tipe termasuk invalid option key dan weighted_choice server-only, no-answer-leak serialisasi, lifecycle lock; `packages/db/src/exam/question-service.integration.test.ts` 12 test lewat pglite — stimulus reuse, image option/assets, XOR owner violation, version immutability penuh draft→in_review→approved→published→archived, maker-checker approval): seluruhnya lulus.
- Tidak membangun attempt engine, scoring engine, ranking, atau tryout batch — question bank model saja. Tidak mengklaim Gate C PASS (OD-04 masih open). Tidak ada route `apps/web`. Lihat ADR-061.

## Bulk XLSX/ZIP question import dengan validasi dan rollback (QST-002)

- **Pipeline dok 15A §7 (9 state async) DIRINGKAS jadi validate-then-commit satu panggilan sinkron**: VALIDATE (read-only — parse workbook+ZIP, cross-check setiap baris terhadap baris lain dan isi ZIP, resolve intent create/update/revise/skip) lalu COMMIT (satu `db.transaction()`, hanya dimasuki jika nol issue). "Import harus rollback kalau ada error" dipenuhi secara struktural: error konten ditangkap SEBELUM ada tulisan apa pun; error saat commit membatalkan seluruh transaksi lewat throw-to-rollback Drizzle. Mode `partial` dok 15A §6 (row valid commit, row error skip) SENGAJA tidak diimplementasikan — didokumentasikan di ADR-062, bukan silent gap.
- **Setiap tulisan di commit phase memanggil fungsi service QST-001 yang SUDAH ADA** — nol write path kedua: `createQuestionDraft`/`updateQuestionDraft`/`setQuestionOptions`/`setQuestionAnswerKey`/`createStimulusDraft`/`updateStimulusDraft`/`addQuestionAsset`/`addStimulusAsset` dipakai ulang tanpa perubahan, plus dua penambahan baru yang strukturnya identik (`createQuestionRevision`/`createStimulusRevision`) untuk dok 15A §6's mode `create_revision` yang QST-001 sendiri belum punya caller-nya. `assertValidAnswerKey`/`assertQuestionVersionMutable` QST-001 berjalan tanpa modifikasi untuk baris hasil import.
- **`resolveImportRowIntent`**: satu fungsi keputusan pure di `@superlatif/domain/exam`, generic atas `RecordStatus` (dipakai untuk question DAN passage) — kode baru→create; draft/changes_requested + mode `update_draft`→update di tempat; draft/changes_requested + mode `create_revision`→skip (belum ada yang published untuk direvisi); locked (approved/published/archived)→hanya `create_revision` boleh, `update_draft` ditolak.
- **ZIP tidak pernah ditulis ke filesystem nyata** — setiap entry dibaca langsung ke Buffer in-memory, storageRef content-addressed opaque (`import-asset:sha256:<hex>`) — zip-slip ditutup SECARA STRUKTURAL, bukan cuma validasi. Validasi path (`assertSafeAssetPath`: tolak `..`, absolute/drive-letter path, backslash, null byte, wajib di bawah `images/<placement>/`, ekstensi executable) dicek terhadap `entry.unsafeOriginalName` jszip (nama RAW sebelum jszip sendiri men-sanitize), bukan `entry.name` yang sudah bersih — kalau cuma cek nama yang sudah disanitasi, traversal check TIDAK AKAN PERNAH melihat serangannya. Satu entry tidak aman meracuni SELURUH arsip (throw langsung, tidak partial-import). Limitation zip-bomb didisclosure eksplisit di ADR-062 (jszip tidak expose ukuran uncompressed sebelum dekompresi).
- **`exceljs`+`jszip` dependency baru di `@superlatif/db`** (bukan `@superlatif/domain` — tetap bebas vendor SDK per `check-workspace-boundaries.mjs`). `xlsx-parser.ts` baca sheet by HEADER NAME (row 1), tahan terhadap urutan kolom berubah. Tidak ada file fixture XLSX/ZIP biner di-commit — setiap test wajib membangun XLSX/ZIP asli sendiri lewat writer API `exceljs`/`jszip`, lalu diproses lewat parser produksi yang sama.
- **Scope yang sengaja dipersempit** (didokumentasikan, bukan silent): numeric min/max range TIDAK didukung (hanya accepted_value+tolerance, sesuai `NumericAnswerKey` QST-001 yang sudah shipped); `passage_code` yang dirujuk question WAJIB punya baris sendiri di sheet Passages workbook YANG SAMA; activation scope/exam family (dok 15A §8) sama sekali tidak dimodelkan (scope EXM-series nanti).
- **Test wajib** (`packages/domain/src/exam/import-*.test.ts` 21 test — path traversal/absolute/backslash/null-byte/extension rejection, mapping tipe workbook↔schema, resolve intent per kombinasi status+mode; `packages/db/src/exam/import/question-import-service.integration.test.ts` 9 test lewat pglite — valid bulk import lintas 5 tipe soal, missing image report, path traversal rejection via ZIP asli, replay idempotency byte-identik vs byte-berbeda, unauthorized rejection, invalid answer key row): seluruhnya lulus.
- Tidak ada route upload/preview/moderation `apps/web` (scope QST-003). Tidak mengklaim Gate C PASS (OD-04 masih open). Lihat ADR-062.

## Batas arsitektur yang ditegakkan mesin

`pnpm run lint` gagal jika:

- sebuah paket melanggar matriks layering (misalnya `packages/domain` bergantung pada `packages/ui`);
- sebuah file mengimpor paket yang tidak dideklarasikan di `package.json` (phantom dependency);
- `packages/domain` memperoleh dependency runtime eksternal apa pun (aturan "tanpa vendor SDK");
- ada direktori workspace tanpa `package.json` atau tanpa script `typecheck`.

## Batas keselamatan

- Jangan mengaktifkan commerce production tanpa OD-01 dan OD-02.
- Jangan mengaktifkan ranked SKD production tanpa OD-04, academic sign-off, Gate C, dan OD-08.
- Jangan menjalankan production migration tanpa legacy evidence, rehearsal, reconciliation, dan Gate D.
- `drizzle-kit push` hanya untuk database lokal yang disposable.
- Semua fixture dalam repository ini sintetis dan tidak menggantikan bukti resmi/provider.
